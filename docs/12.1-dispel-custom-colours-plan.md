## Goal

Restore user-customisable **per-dispel-type colours** for the two surfaces that colour by
dispel type — the **Dispel Overlay** and the **debuff-row icon border** — with the colour
pickers living **centrally on the Colors page** (`display_classcolors`) and every GUI element
that offers custom dispel colours **linking back** to that section via the existing
`GUI:LinkToSetting` / `GUI:CreateColorsPageLink` cross-link + flash.

Custom dispel colours were removed 2026-07-11 (Config.lua:1390 comment) because per-type
colouring needed addon-side reads of a **secret** dispel type. The 68824 datamine removes that
blocker: `SetAuraBorder`'s `customDispelColorMap` / `customDispelColorCurve` (and the already-live
`C_UnitAuras.GetAuraDispelTypeColor(unit, aid, curve)`) colour a border by dispel type
**engine-side** — no addon aura reads — so the whole overlay can be recoloured on one slot,
secret-safe.

## Architecture — one shared resolver, two consumers

Add **one** builder (in `Frames/Colors.lua` or a small `Features/DispelColors.lua`):

```
DF:GetDispelColorCurve(db, useCustom)  -> ColorCurve | nil
```
- `useCustom` is the **per-surface** flag (overlay: `db.dispelOverlayCustomColors`; icon:
  `db.debuffBorderColorByType and db.debuffBorderDispelCustom`).
- Returns **nil** when `useCustom` is false (callers then let Blizzard's native palette apply —
  overlay: no `customDispelColorCurve`; icon: fall through to game colour), OR
- Returns a `C_CurveUtil.CreateColorCurve` built from the six per-type db colours when true.
- Cached (keyed by mode/db) on `DF.dispelColorCurve`; `DF:InvalidateDispelColorCurve()` (already
  exists, extend to clear this too) nils it on any dispel-colour setting change.
- Reads colours from the passed `db` handle (`db.dispelMagicColor` etc. — matches the existing
  per-mode `GetTestDispelColor` reads), so the engine is scope-agnostic; **the Colors-page picker
  scope (account-wide vs per-mode) is a Stage-5 GUI call** (see Open questions).
- One shared `DISPEL_DEFAULT_COLORS` constant (the current game palette values) replaces the three
  hardcoded tables; `GetTestDispelColor` and the OOR path read it.

**Consumer A — overlay:** pass `customDispelColorCurve = DF:GetDispelColorCurve()` into the three
`SetAuraBorder` option tables (only when non-nil). Confirm the exact field name against the 68824
dump — **overlay custom colour is 68824-gated** (the SetAuraBorder field is datamined, not yet
live), so feature-detect and no-op cleanly pre-68824.

**Consumer B — debuff icon:** route `DF.debuffBorderCurve` through `DF:GetDispelColorCurve()` (real
per-type colours instead of the placeholder). `GetAuraDispelTypeColor` is **already live**, so
this half is buildable + testable **now**, independent of 68824.

**Fold in the must-fix:** `AuraButtonBorderStyle` global was **removed** in 68824 →
`Enum.CustomAuraButtonBorderStyle`. The `... or 1` fallback at Dispel.lua:1327 (and the ~9 sibling

## The default-vs-custom selector — DECIDED: per-surface, colours shared

Separate two things: **what the colours are** (shared) from **which surface uses custom vs game**
(the decision). A single *global* toggle was rejected — it has no honest home (placed on the
Overlay page it implies overlay-only; and it would fight the debuff icon's **existing** per-surface
control, "Color by Dispel Type"). So:

- **Colours = shared, on the Colors page.** Six pickers, one source of truth, no global on/off here.
- **The game-vs-custom decision = per-surface**, on each surface's own page, next to its existing
  enable, each with a link back to the Colors page:
  - **Overlay page** — a **toggle** `dispelOverlayCustomColors` ("Use custom dispel colours",
    default OFF). Binary, because the overlay is always type-coloured — game vs custom is the only
    axis.
  - **Debuff-icon page** — keep the existing `debuffBorderColorByType` on/off checkbox and add a
    nested **toggle** `debuffBorderDispelCustom` ("Use custom colours", default OFF, dimmed when
    Color-by-Type is off). *A 3-way Off/Game/Custom dropdown reads cleaner but would retire the
    existing bool → a saved-profile migration, which the house rule avoids. The additive nested
    toggle needs no migration, so take it unless Krathe wants the dropdown + migration.*

Net: **toggle on both surfaces** (each binary once you factor out the icon's separate on/off). Both
draw from the shared six pickers — exactly the "link every element back to the Colors page" model,
with the *decision* kept local where users expect it.
