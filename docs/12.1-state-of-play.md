## Where we are

**End stage.** The pre-12.1 scan/cache aura pipeline is fully deleted; every aura surface —
buffs, debuffs, defensives, missing-buffs, Aura Designer — renders on Blizzard's
CustomAuraContainer / AuraButton engine. Shipped in **v5.0.0** plus the PR #214 hardening rounds on
top (see `CHANGELOG.md` [5.0.0] + the PR body for the full list): the container port, AD rebuilt on
the engine (all specs, combat-safe), Duration Bars, sort controls, hide-permanent-timer, Aura
Duration Update Rate, in-place (no-rebuild) mutators, the Expiry **Border / Tint / Text / Glyph**
reveal, editable duration-colour breakpoints, Buff/Debuff Filters + Filter Designer, the **debuff
blacklist**, boss debuffs in the debuff row, Missing Buffs (combat + M+), the unified **Dispel
Overlay with custom per-dispel-type colours** + Dispel Symbol, test mode through the real engine,
DF-owned border animations, Pixel Perfect, and identity-gate hardening.

## ★ PTR-7 / build 68914 (2026-07-24) — what changed and what it costs us

Source-diffed `fa38386c81`(68824) → `d3915c78ab`(68914) on Gethe + the official dev notes.

+40/-155, new `Blizzard_AuraContainerFlowLayout.lua`.

**★ The `SetDurationText` colour-curve bug is FIXED — smooth colour-by-time is UNBLOCKED.**
`Blizzard_CustomAuraButton.lua:186` now passes BOTH args:
`binding:SetTextColorCurve(options.textColor.curve, options.textColor.property)`.
The option was restructured: `textColorCurve` → `textColor = {curve, property}`
(`DurationTextBindingColorOptions`). Our weekly line-~168 source-diff check paid off on its
first run. Not mentioned in the dev notes — a silent win.

**★ BREAKING (and NOT in the dev notes): `SetDurationText`'s option table was gutted.**
`CustomAuraButtonDurationTextOptions` is now ONLY `binding` / `textFormatter` / `textFormat` /
`textColor`. **`expiredText`, `zeroDurationText` and `updateInterval` are gone from options**, and
`formatter` is renamed `textFormatter`. DF's `bindNative` passes all four old names → on 68914 we
silently lose the formatter, hide-permanent-timer (`zeroText=""`) and the Aura Duration Update Rate.

**→ WE LOSE NOTHING. The options RELOCATED to the binding object.** Verified against
`DurationTextBindingObjectAPIDocumentation` @68914 — the binding retains `SetFormatter`,
`SetExpiredText`, `SetZeroDurationText`, `SetUpdateInterval`, `SetTextColorCurve`, `SetTextFormat`,
`SetTimeModifier`, `SetEnabled`, `SetToDefaults`. The new route: build our own
`C_DurationUtil.CreateDurationTextBinding()`, configure it fully, pass it as `options.binding`
(Blizzard `Assign()`s a copy). **This is exactly the code the test-mode native-duration rework
already produced (`b188714`) — that work is the template for the live migration.**

**★ BREAKING #2 (and NOT in the dev notes): the container-level LAYOUT API was RENAMED.**
Verified against the refreshed local dump (in sync with Gethe): `SetAuraLayoutAnchorPoint`,
`SetAuraLayoutGrowthDirection`, `SetAuraLayoutRowWidth` and `SetAuraLayoutPadding` are **GONE** —
zero hits in the whole `Blizzard_AuraContainer` folder. Replaced by the new
`AuraContainerFlowLayoutSharedMixin` (mixed into `CustomAuraContainerInboundMixin`, so
addon-callable): `SetFlowLayoutAnchorPoint(point)`, `SetFlowLayoutGrowthDirection(h, v)`,
`SetFlowLayoutMaximumLineSize(size|nil)` (the old RowWidth, now axis-agnostic),
`SetFlowLayoutPadding(l, r, t, b)`, plus NEW `SetFlowLayoutAxis(AnchorUtil.FlowLayoutAxis)` —
**the columns feature** — and `ResetFlowLayoutOptions()`. All are live in-place mutators
(`MarkDirty(AuraFrameLayout)`, no rebuild).
**DF impact — SEVERE, SILENT:** `applyContainerLayout` (`Frames/AuraContainer.lua:1226-1246`) wraps
the whole sequence in ONE pcall; on 68914 the first dead call (`SetAuraLayoutAnchorPoint`, :1235)
throws and everything after it never runs — growth direction, wrap and the duration-bar strip
padding are all silently lost. The container still pins (`SetPoint` precedes the throw) but renders
with DEFAULT flow: wrong anchor, wrong growth, no wrap, overlapping bar strips. No error surfaces.
The DF_AuraLab files (`makeStrip`, `pfBuildRow`, the PTR4 probes) call the same dead names.

**★ BREAKING #3: per-group layout options RESHAPED.** `ValidateAuraGroupLayoutOptions` now accepts
`elementSpacing` (along the line), `lineSpacing` (between lines), `groupSpacing`,
`groupLineSpacing`, `forceNewLine`, `elementWidth`, `elementHeight`, `layoutIndex` (layoutIndex
moved INSIDE layout options). **DF's `buildGroupLayout` passes `elementSpacingX`, `elementSpacingY`
and `gapX` — all three are now dead keys** (validation ignores unknowns; they just don't apply), so
icon spacing silently collapses to engine defaults. Mapping: `elementSpacingX`→`elementSpacing`,
`elementSpacingY`→`lineSpacing`, `gapX=0`→`groupSpacing = 0` (re-verify the multi-filter
doubled-gap fix under the new model). **`elementWidth`/`elementHeight` SURVIVE** → the strip
reservation (elementHeight = sy + resv) still works. NEW `forceNewLine` = per-group line break —
multi-row arrangements inside one container (a future consolidation option, not needed now).

**Survivals verified on the dump (things that did NOT break):** `initializeFrame` +
`maxFrameCount` in AddAuraGroup options (unchanged); every `SetAuraGroup*` in-place mutator

**Expiry Border/Tint/Text/Glyph + colour BUCKETS all SURVIVE UNCHANGED.** Both features are `|T`
texture escapes and `|c` colour escapes baked into `NumericRuleFormatter` breakpoint format
strings; the formatter is still first-class (`textFormatter` option, `SetFormatter` on the binding,
and `DurationTextBindingFormatComponent.formatter` is typed `NumericFormatter`). The escape
mechanism did not change. Only the *option name* carrying the formatter moved.

**New expressive power on top:**

- `DurationTextBindingProperty` now has 7 members (RemainingDuration / RemainingPercent /

**1. ⏸ Targeted Spells — ON HOLD (Krathe, 2026-07-24). Do NOT start this.**
The work itself is understood and still the technically best answer, but the *feature's future* is
now the open question, not its implementation. **If no workaround lands, the whole Targeted Spells
feature is a candidate for REMOVAL** rather than repair — Krathe's call, and nobody should sink time
into rebuilding a feature that may be deleted. Revisit only when Krathe says the hold is lifted.

Kept for whoever picks it up later: PTR-7 makes `UnitClass`/role/race/sex secret when identity is
secret, which kills `ReadTargetFingerprint` (`Features/TargetedSpells.lua:1176`) and with it the
per-frame targeted icon in M+ — exactly where it earns its keep. The replacement would be strictly
better than a fix: if `UnitIsUnit(casterTarget, unit)` returns a **secret boolean**, each frame's
icon can be driven by `SetAlphaFromBoolean` without ever learning who the target is — no class
reads, no ambiguity when two Warriors share a spec, no `#matches ~= 1` bail-out. DF already has that
plumbing (`Features/ElementAppearance.lua:104`), so it would DELETE the fingerprint machinery rather
than add to it. Gate: one in-game probe of what `UnitIsUnit` returns under a secret identity.
`Features/TargetedSpells.lua` is 5,767 lines — the largest single removal candidate in the addon,
which is part of why the remove-vs-repair decision is worth taking deliberately.

**2. ★ Tooltip anchor + hide-in-combat — NEXT UP (Fable).** *(Good value · small cost · no probe.)* Pure win on tooltips
users already have. `SetTooltipAnchorPoint` / `SetHideTooltipInCombat` are on the **shared** mixin
(callable on our buttons), are plain mixin state (**not** creation-frozen, so live-togglable with no
rebuild), and directly answer the standing complaint that aura tooltips occlude the raid frames
mid-pull. The `config.tooltips` seam already exists — this is spec fields + GUI, no architecture.

**3. Stable aura order — `AuraContainerSortMethod.AuraInstanceIDOnly`.** *(Good value · small cost.)*
Instance IDs are assigned in application order, so this is chronological, never-reshuffling order —
icons stop jumping when auras refresh mid-fight. `DF:BuildAuraSort` is a clean 12-line mapper and the
Sort Order dropdowns are already in place on both rows and AD group cards, so this is one branch plus
one option per dropdown.

**4. Probe the three "resolved" workarounds.** *(Value = deletion · cost = probes.)* Each may retire
hardening built for a bug Blizzard has since fixed: `_queueOp` combat deferral (5 refs), the
`safeHideWindow` hover-visibility channel (5 refs), the dispel secure-`onInit` architecture (6 refs),
and — the big one — `ResizeToBoundsRect` against the missing-badge window-park + `/df ppbadge`
self-size workaround (13 refs). All in `Frames/AuraContainer.lua` (3,472 lines), our most complex
file. **Probe before touching, and retirement is Krathe's call** ([[feedback_dont_retire_without_asking]]).

**5. Multi-component duration text ("12s (45%)").** *(Moderate value · now small cost.)* Materially
cheaper than when it was written: `applyDurationFormatter` already routes `textFormat` with
components, because the percent-unit expiry reveal needed it. A second component is a spec + GUI
change on a path that is built and in use.

**6. Multiple dispel textures per button.** *(Low value · medium cost.)* Legal now that
`AddDispelTypeTexture` is plural, but our overlay was rebuilt around owning one carrier and the
secure-init dance; a second cue means re-opening that. Park until #4 tells us whether the secure-init
architecture survives at all.

**Deliberately NOT building** (recorded so they don't come back): global aura-tooltip styling (it
restyles *every* addon's tooltips — not ours to change), weapon enchants (a self display, not a
raid-frame one), `SetAuraBorder` colour curves (datamine 68824: dispel-type, **not** time — `|T`
stays the only expiry-border path).

### ★ NEW CAPABILITIES PTR-7 opens — feature candidates (2026-07-24)
All API-verified against 68914 source, not the dev notes alone. Tiered by value to a *raid-frame*
addon; the Tier-2 rejections use the same "is this a raid-frame thing?" test that parked
`SetSpellName` / `ApplicationBar` / right-click-cancel.

**TIER 1 — build these.**
- **★ Aura button TOOLTIPS are viable again — the parked plan is unblocked.**
  `AuraButtonSharedMixin:SetTooltipAnchorPoint(point, offsetX, offsetY)` and
  `SetHideTooltipInCombat(hideInCombat)` (+ the `Get`/`Should` readers) are on the **shared** mixin,
  so they are callable on OUR buttons. They genuinely drive behaviour:
  `AuraButtonPrivateMixin:ShouldShowTooltip()` returns false when
  `ShouldHideTooltipInCombat() and UnitAffectingCombat("player")`, and `ShowTooltip()` does
  `tooltip:SetOwner(self, self:GetTooltipAnchorPoint())`. Content is
  `tooltip:ShowAuraTooltip(unitToken, auraData)` — **native, therefore secret-safe by construction**.
  *Both historical blockers are now gone:* occlusion of the raid frames mid-pull → fixed by anchor
  control; the hover-while-visibility-changes Lua error → "resolved" per the dev notes. This takes
  `docs/aura-designer-tooltips-plan.md` (scoped, never built) off the shelf.
  ⚠ Caveat: TEST MODE deliberately disables native hover (it would tooltip the hidden SAMPLE aura,
  see `_paintTestSlot`) — tooltips are a LIVE-path feature only, and the DF-owned test hover tips stay.
- **Column layouts for aura rows.** `SetFlowLayoutAxis(AnchorUtil.FlowLayoutAxis)` — container-level,
  live in-place (`MarkDirty`, no rebuild), lands naturally in `applyContainerLayout` during the
  layout migration. Buffs in a column beside the frame instead of a row across it — a real
  raid-frame want. (Per-group: `forceNewLine` + `layoutIndex` + `groupSpacing`/`groupLineSpacing`
  allow multi-row arrangements inside ONE container — a future consolidation option, not needed for
  DF's one-group-per-container architecture.)
- **Stable aura order — `AuraContainerSortMethod.AuraInstanceIDOnly` (= 8).** UPGRADED from the
  earlier "marginal" verdict: instance IDs are assigned in application order, so this is
  **chronological, never-reshuffling order** — icons stop jumping around when auras refresh
  mid-fight. A genuine user-facing sort-dropdown option (comparator:
  `AuraUtil.AuraInstanceIDOnlyAuraCompare`).
- **Multi-component duration text.** `SetTextFormat(formatString, components)` where each
  `DurationTextBindingFormatComponent` samples its OWN `property` with its OWN `formatter`. So
  "12s (45%)" in one native, secret-safe string. Pairs with the 7-member
  `DurationTextBindingProperty` (RemainingDuration / RemainingPercent / ElapsedDuration /
  ElapsedPercent / TotalDuration / StartTime / EndTime) — colour and text can key off elapsed or
  total, not just remaining.
- **Multiple dispel textures per button.** `AddDispelTypeTexture` is plural now (`SetAuraBorder` is
  a compat shim over `ClearDispelTypeTextures()` + `AddDispelTypeTexture`). Our overlay binds ONE
  carrier and has had to fight for that single slot; layering a second cue is now legal.

**TIER 2 — available, but rejected/parked on value (reasons recorded so we don't re-litigate).**
- **Weapon enchants** — `AddItemEnchantment(itemEnchantmentSlot, options)`,
  `SetItemEnchantmentSortMethod`, `SetItemEnchantmentLayout`, `ResetItemEnchantmentLayout` (+ a full
  set of `AuraContainerUtil.GetItemEnchantment*` / `CompareItemEnchantments*` helpers). Brand-new
  first-class container feature, but it is inherently a **self** display (your own poisons/imbues),
  not a raid-frame one — same test that parked `SetSpellName` and the stacks bar.
- **Global aura-tooltip styling** — `AuraContainerUtil.SetTooltipNineSlice` / `SetTooltipBackdrop` /
  `SetTooltipTextureSlice` / `GetDefaultTooltip` / `ClearTooltipStyle`, with
  `C_AuraContainerUtil.ProcessAuraTooltip*Options` and the `AuraContainerTooltip*Options` structs
  (incl. `anchorOffsets` for the backdrop/slice corners). **The dev notes are explicit these are
  GLOBAL, not per-container** — using them restyles EVERY addon's aura button tooltips. Reject on
  principle: not ours to change. (Distinct from the per-button anchor/combat APIs in Tier 1, which
  ARE ours.)
- ~~Aura-instance-ID sort method~~ — **UPGRADED to Tier 1** (2026-07-24 second pass): it's stable
  *chronological* order — no mid-fight reshuffling — which users actually ask for. See Tier 1.

**Small extras confirmed on the dump (grab when convenient):**
- Tooltip anchors accept the FULL `ANCHOR_*` set including `ANCHOR_CURSOR` /
  `ANCHOR_CURSOR_LEFT/RIGHT`, and both tooltip settings are plain mixin state — **not
  creation-frozen**, togglable live without a rebuild. The native path also tooltips item
  enchantments (`SetInventoryItem`).
- `AuraContainerInbound.GetDefaultAuraDurationFormatter()` — Blizzard's default duration formatter,
  addon-readable; useful as the fallback in the binding migration.

**PERF / better-way notes out of the second pass:**
- **One binding per style-signature, not per slot** — `options.binding` is `Assign()`-copied by the
  engine, so the migration can hold a single configured `DurationTextBinding` per row style and

- **`SetAuraGroupLayout` may make size/spacing edits in-place** — today any layout edit changes the

- **All `SetFlowLayout*` setters are live mutators** — anchor/growth/wrap/padding changes need no

  rebuild-vs-restyle split can lean harder toward restyle after the migration.
- **`ResizeToBoundsRect`** — if it sizes a parent over secret-rect children, the missing-badge
  window-park hack and parts of the pp self-size workaround collapse into one API call.

## ★★ Blizzard roadmap (dev Discord, 2026-07-24)

Relayed by Krathe from the Blizzard dev Discord. **This is a roadmap, not API documentation** —
every claim below needs verifying against the next build's source before anything is planned on it.
Recorded here so the 12.1.5 half can be re-read months from now without re-deriving it.

### Landing in 12.1 — check the next build (~1 week out)

Krathe wants eyes on both the moment they appear.

1. **Pandemic indicator support — TEXTURES ONLY** (animations deferred to 12.1.5).
   **Not a replacement for our expiry reveal; additive.** Pandemic is ~30% of an aura's *base*
   duration — the window where a refresh rolls over remaining time instead of clipping it. We
   **cannot compute that ourselves**: base duration and remaining are both secret on 12.1. Our
   Alert Below is an arbitrary user threshold, and it carries Text/Glyph modes this won't cover.
   Two different questions ("warn me soon" vs "refreshing now isn't a waste"), and for a healer
   deciding when to re-apply a HoT theirs is arguably the more correct signal.
   **★ The real prize:** if this is a genuine texture on the button rather than an inline escape,
   it sidesteps `|T` being **font-coupled** — the constraint that makes our reveal square-only in
   practice and collapses it on a thin target such as a bar (`frame-level-tint-exploration.md`).
   That would be the first true alternative to the `|T` companion since the 68824 datamine closed
   the `SetAuraBorder`-curve door (those curves turned out to be dispel-type, not time).
   **Answer from source before designing:** fixed 30% / per-spell / configurable? per-button or
   per-container? a texture object we style, or an atlas we pick from?
2. **`container:SetEnabled(false)` should reset/remove all aura buttons.**
   Touches our teardown path and could simplify it — but probe before trusting it. Our
   combat / SetEnabled-last discipline exists for a reason.

### Deferred to 12.1.5 — likely months away

**Do not plan v5 around any of these.** Re-read this list when the 12.1.5 PTR opens.

| Item | Note for us |
|---|---|
| Pandemic **animations** | The 12.1 item is textures only. |
| **enable/disable methods for groups/slots** | Blizzard acknowledge "some (ugly) workarounds" in the meantime — which confirms our `excludeSpellIDs` + rebuild approach **is** the intended 12.1 state. Stop looking for a cleaner one. |
| `isHostile` / `isFriendly` candidate filters | Based on the container unit. |
| `casterIsFriendly` / `casterIsHostile` candidate filters | Based on **`AuraData.casterUnit`**. ★ The load-bearing detail is `casterUnit` **existing at all** — our source-relative identity gate (`PLAYER` token / `isFromPlayerOrPlayerPet`) fails open across instances *precisely because* the caster can't be attributed. Worth asking whether it's readable where our gate currently gives up. |
| group/slot `:SetUnit` | e.g. combining `player` buffs with `target` debuffs in one container — interesting for pinned / personal surfaces. |
| `auraButton:SetApplicationBar` option `minApplications` | Our ApplicationBar want is confirmed, but 12.1.5 — so it stays off the v5 plan. |
| `auraButton:SetCasterName` | Plus caster name (class-coloured) as a tooltip line. |

### "No comment" — they didn't commit either way

- Append info to tooltip — Blizzard: *"unlikely we'll ever get that."*
- **`showStealable` border** — added late; they'll ask internally.
- Option to show an enchantment icon instead of the item it's applied to.
- **Alpha / scale / saturation curves — ★ they say a clear use-case example is what's missing, and we have one.**
  Our expiry reveal **cannot blend**: `|T` inline textures ignore the fontstring vertex colour a

  step — the entire reason the Colours page has to *tell* you borders always step. An alpha or
  saturation curve on the button closes exactly that gap. Concrete, in production, screenshot-able.
  **Worth writing up and sending back.**

**Build now — was CLEARED 2026-07-22, REOPENED by PTR-7.** Every *pre-PTR-7* engine-ready item was

**Parked — out of scope for a raid-frame addon (Krathe, 2026-07-22):**
- Spell-name text on aura buttons (`SetSpellName`) — too cramped on small raid aura icons.
- Right-click cancel own buffs (`SetCancelAuraButtons`) — a personal/player-frame behaviour, not a raid-frame one.
- Stacks bar (`ApplicationBar`) — the stack *count* already shows on the icon; a separate bar is cramped/redundant on small raid icons.

**Investigated & rejected — verified against the code/API, not worth building (2026-07-22):**
- Idle-frame perf `SetOnUpdateMode(RunWhenVisible)` — **no-op on our code.** Border anims already run on ONE
  shared UIParent driver that skips hidden borders in-loop (`border:IsShown()`, `Frames/Border.lua:637` comment
  shows the author already designed around `onUpdateMode`); the expiry reveal is engine-native (no DF ticker);
  the AFK/BG-carrier tickers are single, shared, throttled on always-shown hosts. Nothing to suspend. (Only tiny
  opt left: self-suspend the shared border driver when zero anims are active — marginal, not taken.)
- Auto-seed Missing Buffs from `C_CooldownViewer.GetGroupBuffItems()` — **no value over our static list.** The API
  is scoped to the *player's own spec* buffs, so it can't power the cross-class missing-buff audit (on a Priest it
  returns only Fortitude — nothing about Intellect/AP/Skyfury/etc.). It could only self-maintain the "detect my
  buff" default; the hand-maintained `DF.RaidBuffs` (6 rows) is low-churn and still needed for manual mode + as the
  fallback, so the swap isn't worth it.
- `layoutIndex` group ordering — **no user gap.** DF anchors each aura row independently (cross-row order = DF's own
  anchors, not `layoutIndex`), and within-container order is covered by the native sort controls + registration
  order. `layoutIndex` only reorders groups sharing one container flow — a case we don't expose to users.
- `CanBeAccessedInContext` / `HasAccessConstraints` gate cleanup — **can't help.** The return is secret-for-
  `ObjectSecurity` (a secret bool → can't branch on it in Lua), and it concerns *our* access to an object, not the
  actual hover root cause (Blizzard's own tooltip intrinsics indexing secret aura data on `OnEnter`). The shipped
  pcall-and-defer gate is hardened + in-game-verified — no reason to destabilise it.
- In-combat `SetAuraGroupFilterString` — **low value.** It's a group-mixin method
  (`AuraContainerAuraGroupMixin:SetFilterString`), combat-safety unverified; changing filters mid-fight is a rare
  action and the combat-end deferral is acceptable. Not worth the risk.
- `C_Roleset` visibility — **don't rebuild working code.** `ApplyRolesetFilters(blocked/allowed)` is a role-content
  filter — a different problem from the cross-faction identity gate DF already solved. Replacing a hardened
  visibility channel on spec risks reintroducing the taint/hover bugs just fixed.
- Delete "fixed-bug workarounds" — **nothing to remove.** DF's "FormatNumber guards" ARE the correct secret-safe
  design (native `SetDurationText`/`SetApplicationCount`, never `string.format` on secret remaining) — removing
  them reintroduces the secret trap; the "swipe workaround" was our own direction *fix* (`SetReverse`), not a
  Blizzard-bug patch; `tooltipShowAuraSpellIDs` was never built (a minor dev cvar, not worth it).
- Radial / pie expiry indicator — **redundant or blocked.** DF already ships the native cooldown swipe
  (`SetDurationCooldown` → engine-bound radial depletion on the *secret* remaining time, with a Hide-Swipe toggle).
  `SimpleAnimRadialProgress` is a manual from/to-percent animation with no native aura-remaining bind, so a bespoke
  ring would need the secret remaining time to drive it. **Precision (2026-07-23):** the blocker is the secret
  *data*, not a missing API — the duration machinery IS addon-callable (`C_DurationUtil.CreateDuration` +
  `SetTimerDuration`, proven in test mode above), but a LIVE aura's duration object is built inside
  `CustomAuraButtonPrivateMixin:UpdateAuraDisplay` as a **local**, filled via `secretwrap`, and handed straight to
  the bindings — never stored on the button, so there is nothing to fetch, and passing a secret one from addon
  (tainted) code would violate `AllowedWhenUntainted` anyway. Don't re-probe the API; only a native bind unblocks it.
